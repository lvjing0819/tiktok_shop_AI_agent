# 离线容器执行器与定价接入

## 范围和信任边界

保留Leader/业务Agent、Harness、受控业务服务。新增Docker执行器，首版仅运行随代码审核的固定JSON任务：定价和受控隔离验收探针（PID上限、内存OOM及带子进程的超时回收）。探针不向Agent工具注册表暴露。没有通用Python/Shell执行接口，不支持模型选择镜像、命令、挂载或网络配置。媒体生成、任意文件输出、联网沙箱、microVM和gVisor均未接入；固定小型JSON文件已在[v0.11文件产物层](sandbox-files-v11.md)补充，以下JSON-only边界以该补充为准；不修改看板、记忆或选品。

定价流程：受控业务服务读取已确认商品/SKU/仓库/库存/成本/内容快照，向容器仅提供成本、费率、可售数量和渠道上限；容器执行原定价公式；服务重新读取并比对全部快照，确认版本和可售数量未变化后，才保存上架草案。计算期间不持有数据库写锁。定价工具版本升级为3，旧版本调用回执不应作为新执行复用。

当前业务网关仍是受信任后端内的固定工具函数，不是新建的独立网络服务；容器完全不持有应用数据库和平台凭据。后续如接入联网沙箱，必须增加独立身份、能力授权和受控出口，不能把现有函数封装称为已完成的联网安全网关。

## 固定容器策略

- 镜像标签固定为`tiktok-shop-agent-sandbox:v2`，创建前解析不可变镜像ID并检查项目标签。Agent无法传入其他镜像。镜像构建上下文仅包含`sandbox/Dockerfile`和`worker.py`，不会发送项目`.env`或数据库给构建器。
- 无任何宿主bind挂载，无Docker socket，无应用环境变量；通过stdin传不超过64KiB的一行JSON，stdout最多32KiB。额外环境变量（包括Docker客户端自动注入的代理）会在启动前被拒绝。
- 根文件系统只读、用户65532、cap-drop ALL、no-new-privileges、默认seccomp、独立PID/IPC/UTS/cgroup视图、网络none。不发布端口。
- 1核CPU、1GiB内存、禁用额外swap、最多64任务/线程。`/work`是128MiB有界tmpfs，`/tmp`是16MiB；两者nosuid/nodev/noexec。Docker日志驱动关闭，执行器只接收有界输出，审计保存校验值和元信息，不保存原始成本或任意日志正文。
- 每次启动前检查Docker实际创建配置；容器内再读取cgroup v2额度、Seccomp/NoNewPrivs/CapEff、UID、只读根和网络状态，额度不生效则拒绝工作。需支持cgroup v2的Docker环境。
- 使用普通用户不等于配置了Linux User namespace映射。本策略不强制User namespace remapping，验收返回实际UID映射，不声称这一层已实现。
- 文件产物补充提供固定定价JSON文件收集与校验，不把容器返回路径当宿主路径读取。图片/视频仍未接入，不能按现有JSON校验直接放行。

## 生命周期与失败语义

一条`sandbox_run`关联workspace、run、step、attempt，保存策略/镜像版本、输入输出校验、时间、退出码、OOM标志与worker报告的CPU/峰值RSS。后者是固定worker报告的进程统计，不是所有子进程的完整容器监控。

容器外计时。超时、取消或执行尝试失效时，先给予3秒正常停止，再强制停止/删除并向Docker确认不存在。终止Docker客户端不等于终止容器，因此独立执行回收。Docker断连不能当作“容器已不存在”。回收未确认时，同一运营任务的新沙箱被阻止，避免旧执行仍运行。

无论成功失败，结果都必须在当前执行尝试仍有效时提交。超时通过结构化observation返回：原因、耗时、sandbox_id、停止确认、外部副作用（离线作业为none）、允许动作。Agent可提出ask/stop，Harness持久化受阻/待确认状态。首版不自动重试、不自行增加资源额度或改变输入；模型复核失败也保留原始超时事实。手动继续会创建新步骤执行身份和新容器，不恢复任意脚本的内存进度。

worker的独立维护线程每10秒核对本机记录中的沙箱（不在业务同步主循环内等待Docker），仅回收超过期限、租约失效、任务停止或attempt变化的项目容器；删除前再次核对完整项目标签。同时按项目标签发现迟到创建的容器，与已保存执行记录核对后回收。项目标识包含本地项目路径的哈希，避免不同项目副本误清理；它不是Docker全局prune。若删除前整个后端崩溃，启动后可根据记录恢复核对。Docker不可用时保持未确认状态；不会绕过沙箱在宿主计算。

## 安装、构建与真实验收

在项目目录、Docker Desktop已启动后运行：

```sh
.venv/bin/python -m scripts.setup_sandbox
RUN_DOCKER_SANDBOX_TESTS=1 .venv/bin/python -m pytest tests/test_sandbox.py -q
```

第一条只用最小上下文构建镜像，然后运行使用8任务上限的真实容器，实际验证进程创建被限制，并校验非特权UID、seccomp、网络、只读根、cgroup额度和UID映射。Linux上的Docker Engine也可使用。应用不自动安装Docker、不接受许可条款，也不会自动拉取缺失镜像；不可用时返回明确阻塞状态。

第二条在pytest的临时数据库中执行真实隔离、64MiB限额下的OOM、带子进程的超时回收及商品定价交接，不读取实际店铺数据。普通测试使用伪Docker边界，仅证明配置、生命周期和业务逻辑，不能替代真实隔离验收。

部署时API和worker需要使用同一新版本，worker账号需能访问Docker daemon（属于受信任控制权限）。不能把Docker socket交给任务容器。现有任务中心可查看沙箱审计记录；没有后台执行器时，周期回收不会运行。

## 接口

- `GET /api/sandbox/status`：运行环境、镜像和策略状态，使用工作台访问控制；ready仅表示可用前提，实际隔离以容器验收为准。
- `GET /api/operations/{id}/sandboxes`：工作区内任务的最近100条执行元信息。
- 没有任意容器创建、任意命令、文件挂载或网络策略修改HTTP接口。

## 验收状态

真实Docker测试是否通过，必须以当前环境实际运行结果为准。安装或系统权限步骤尚未完成时，只能报告代码/模拟边界测试通过，不能声称沙箱隔离已经生效。当前尚未替代原商品演示工作流，也不改变其模拟能力；首版只接运营任务的`product.prepare_listing`。
